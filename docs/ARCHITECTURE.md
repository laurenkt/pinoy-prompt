# Architecture

How Pinoy Prompt is put together, and the rules that keep it one app rather than a set of features that happen to share a page. The README says what the app does; REVIEW.md says what a change must not break. This says where things go.

Two rules come first:

- **Extend the system that already does the job.** Before adding a module, find the one below that owns that kind of work (audio, storage, navigation, layout, tests) and grow it. A second way of doing the same thing is a bug waiting for the two to disagree.
- **Rule of three.** Copy something once if you must; the third copy becomes a shared piece. Don't build a shared piece for one or two users.

## The systems

Each system has one owner module. Anything else that needs it calls that module.

### Navigation and page layout

Every screen is one of two kinds, and each kind has one layout:

- **A page** (Library, Settings): opened from Home, browsed, left. It starts with `pageHeader()` from `ui.ts`: the back arrow (`.back-bar`) at the top left, then its title with at most one control beside it (`.page-header`). System back goes Home.
- **A session** (Study, a drill round, Chat): something in progress. It has `.session-header` with the close button (×) at the left, then progress and any controls. Close, and system back, end the session the way the screen chooses (Study shows its summary, a drill round goes Home). Drills open straight into a round, so they are a session; only with too few words to drill do they show a page saying so.

Home is the hub and has its own header. A screen never shows both a back arrow and a close button. New screens pick one of the two kinds; a new kind of screen is a decision worth writing down here first.

**Header buttons.** Icons in a header are `iconButton` from `ui.ts`; a toggle passes `pressed`, and turns teal while it's on. Quiet mode (`quietToggle`) is the one split button, on Home, Study and Drills alike: two halves the size of an icon button sharing an outline, the mic and the sound, each pressed (teal, its icon crossed out) while it's off. On Home it floats under Settings with the greeting flowing around both, so the greeting's first word keeps its width. Home's settings button is a toggle too: Settings passes it, on, to `pageHeader`, which draws it at the right of the back bar, where it sat on Home, so a second tap closes Settings. It goes Home like the back arrow beside it, on purpose, so the toggle reads as one. A page opened from another header toggle on Home would do the same.

**Height.** Every screen is at least as tall as the phone's screen (`.screen` in `style.css`, under "Layout"). A screen that fits passes its spare height down a column of containers (`.home`, `.practice`, `.talk`, `.session`, `.session-body`, `.panel`) to what can use it, so a taller phone gets bigger targets rather than an empty bottom:

- In a session's `.panel`, the prompt grows on phones taller than about 700px, answer choices share the rest (up to a size a thumb can't miss, leaving room below for the feedback an answer brings so a right answer doesn't move them), and otherwise the panel's last piece (its button, the answer and ratings) sits at the bottom, under the thumb. A speaking question ready to listen, listening or checking takes the spare height itself and puts one big button in its middle, where a resting thumb is, to start and stop in the same place, with room under it for Cancel, which throws the take away without counting it (`.speak.listening` in `style.css`). A `.panel.center` card sits in the middle instead: it is the one look for a message with a way forward (a summary, a topic's introduction, waiting for the microphone, "learn some words first" on Drills and Chat). A wrapper between the screen's root and such a card takes `.fill` so the height reaches it.
- On Home the hub takes it; in a call, the transcript.
- Pages (Library, Settings) are as long as their content and scroll.
- A screen that fits doesn't bounce: `src/fit.ts` keeps `fits` on the page while there's nothing below the fold, and style.css turns off overscroll then. Once a screen runs long (a wrong answer's feedback, Library) it scrolls and bounces as iOS always does. Sizes that grow are worked out from `--fill`, the phone's height less the status bar and home bar, so a screen that fits on an installed iPhone doesn't scroll by the insets. `npm run screenshots` emulates those insets and reports any screen that scrolls, so one that should fit but is a few pixels over shows up.

A new screen or panel gets this by using those containers; a wrapper element between them breaks the column, which `src/screens/layout.test.ts` checks. Sizes that should grow with the phone use `dvh` in a `clamp()`, so on a short phone (375×667) nothing is taller than it was; only answer choices use what little room is left, until one is picked.

Spacing, gutters, tap targets and colours come from REVIEW.md and the `:root` tokens in `style.css`.

**Text you can copy.** The app has two kinds of text. Controls and chrome (buttons, chips and pills, toggles, Library's topic headings, page and session headers, Home's memory card with its chart and labels, other charts, the end-of-session stats) don't start iOS's text selection or its callout when a thumb rests on them. Content (Tagalog words, translations, examples, eyebrows, feedback, error messages, Home's greeting, the Chat transcript) stays selectable so it can be copied. One rule near the top of `style.css` lists the chrome by element (`button`, `label`, `summary`, `nav`, `svg`), by role (`radio`, `img`, `progressbar`, `meter`) and by a few classes that are only ever chrome; everything else is content by default. So a new button or chart is covered without doing anything; new chrome that is none of those joins that list rather than getting a `user-select` of its own, and content never needs marking. Don't add a styling class that content also uses (`.eyebrow`, `.muted`). The rule below it lets two things back in: text fields, because iOS won't let you type or paste into a field inside unselectable chrome, and the word buttons in a Chat message, which are part of the message. Other text on a control can't be copied, so a word the learner might want to copy belongs beside its button, not on it. The results screen's word is a scrubber (a `slider`), so it is chrome; the word can be copied on the card it came from. `src/screens/layout.test.ts` checks both kinds on Home, Study, Drills, Library and Settings.

### Audio

Every recorded sound the app plays goes through `audio-engine.ts`'s shared context: card clips, the right-answer chime and the button tick (via `speech.ts`), slices of a recording (via `player.ts`). So do the results screen's single sounds, made as they play by `phone-synth.ts` and held as long as a finger is down: `playLive` gives them the same fades and the same "playing" bookkeeping as a clip. The chime lives beside card audio so it shares its mute, and so a word clip said back with it starts once it ends rather than over it. The tap sound (a thock for the big chunky buttons, a recording inlined as a data URL from `src/sounds/`; a lighter click made in code by `clickSamples` for chips, pills, section headings, links and checkboxes) is played for every press by one listener (`tickOnPress`, installed in `main.ts`), not by each screen: it stays quiet when the press already used the shared context (a word, the chime, a slice: `audioBusy`), when Settings' Tap sounds is off, while the microphone is in use, and for buttons marked `data-no-tap` (ones that start recording, and the results screen's hold-to-hear button, which makes its own sound). Buttons that may open the microphone (starting a Chat call, opening Drills, turning the Speak chip or the mic on in a drill round) are marked `data-tap="before"` and tap before their handler opens it. A finger scrubbing across the memory chart ticks at each day, like a picker wheel (`detents`), and across the word or the recording on the results screen at each sound; all three take the same gesture from `scrubbable` in `speech.ts` (sideways scrubs, up or down scrolls, a tap is a press): a quieter click, at most every 45 ms, with a haptic tick where the phone allows. A drag can't start audio on iOS, so it only ticks once the app's audio is already going; the scrub gets it going as it begins (`readyDetents`), and a tap on the chart clicks like any press. The results screen's hold-to-hear starts on the finger going down for the same reason it can't always be heard then: if the context hadn't started, it plays from the finger lifting, for a tap's length (`TAP_MS` in `player.ts`). Once the context is made or woken (it's suspended after `IDLE_SUSPEND_MS` idle and closed when the app is hidden), an iPhone takes a moment to start its output, and a word started at once loses its first sound ("Kailan" heard as "ailan"), so every sound but the tap waits `WAKE_SECONDS` after a wake (`startTime` in `audio-engine.ts`). Screens never make an `AudioContext` or an `Audio` element; they call `play`/`stop` for cards, or a `Player` for the results screen. `speech.ts` also owns one path outside the engine: the built-in voice (`speechSynthesis`), used only when a clip can't play. Other exceptions are deliberate:

- `recorder.ts` keeps its own context, made inside a tap, because iOS changes the hardware rate when the mic opens. One made while the microphone was already open is kept (suspended between takes) for as long as that stream lasts, until the screen is left or the app is hidden, so later takes and warm-ups needn't wait for a new one.
- Chat's AI voice is a WebRTC stream, played by an `<audio>` element from `openai.ts`, and `visualizer.ts` makes a context for its analysers. If Chat's audio is reworked, move the analysers onto the shared context or note here why they can't.

`app.navigate` stops card audio, recording and any call, and ends a screen's hold on the microphone, so a screen doesn't have to clean those up when it's left.

**Asking for the microphone.** The phone's permission question comes as a round starts, not over a speaking question. When a drill round that may ask to speak opens, the screen calls `askForMicrophone` from `speak.ts` inside that tap, and it holds the microphone until the screen is left (`holdMicrophone`). If the browser would ask (`microphoneAllowed` in `microphone.ts`, which follows what WebKit remembers), it shows `micWaiting` while the phone asks; if not, the hold is taken quietly anyway, since what WebKit remembers runs out after a few minutes and the round would otherwise ask over a speaking question later. A tap after that only asks again once what WebKit remembers has lapsed (the stream closes in the background). A later tap that lets a round ask to speak again (the Speak chip, the mic going on) asks the same way. If it's refused, speaking is left out until the screen is left. Chat already opens the microphone from its own tap. If the Allow lapses mid-round (a long while in the background), the phone asks again at the next Tap and speak. A new screen that records asks the same way.

**A microphone that gives nothing.** A held stream can outlive what iOS does to the audio session around it, and come back from a tap looking live but giving only exact zeros, or the recorder's context may never start. A working microphone always picks up some hiss, so `recorder.ts` watches for that: with nothing at all `SIGNAL_WAIT_MS` after it starts, it drops the stream (`dropMicrophone`, which closes it so the next `getMicrophone` opens a fresh one) and listens on a new one (`onRestart`, so Speak can ask the learner to say it again); if that gives nothing too, or the take is stopped over exact silence (no screen offers a stop before the microphone gives sound, see below, but a time limit can), the take fails as `'silent'`, which the screens show as its own problem (`PROBLEMS` in `speak.ts`) rather than as "Didn't catch that", and the next tap starts on a new stream and context. A new screen that records gets this by using `record`.

**Saying when it's listening.** Between the tap and the microphone giving sound (switching it on, iOS handing over the audio session, the recorder's context starting) anything said is lost, so a screen never tells the learner to speak from the tap. `record` calls `onListening` once the first sound arrives (the same hiss `SIGNAL_LEVEL` looks for), and only then does a screen say so: Speak shows "Getting the mic ready…" over a waiting button, then turns the prompt card magenta and its big button saffron with "Listening. Say it now!"; a meaning said into Drills' box shows an empty cream box, then a saffron one with "Listening…", where thin bars are added from the left only while there's speech (`onLevel` gives each block's level, whether it's speech, and finer levels for its parts), merging in pairs to fit once they reach the right. Until then Speak's big button can't stop the take and a second tap on Drills' microphone throws it away, as Cancel does on both. A new screen that records waits for `onListening` the same way.

**Warming up.** That gap can mostly be skipped. A Speak question calls `warmRecorder` as it comes up, inside the tap that brought it (Next, the Speak chip) when there is one, and again whenever it's ready to listen: with the round's microphone already held (it never asks), the tracks are switched on and run into the recorder's context, the sound thrown away, and the take that follows adopts both as they are, so it starts with sound already flowing. A question that came up by itself (after a right attempt) can only warm a context an earlier tap started, which WebKit then lets resume. It's cooled for a result or a problem, and when the question goes, the mic is turned off (`setWarm`), the screen is left or the app is hidden, and after a minute unused (`WARM_MS`). It only warms a live, held stream (`liveMicrophone`), and keeps the recorder's context only for the stream it was made under. While it's warm the microphone counts as in use, so presses on that question make no tap sound. Drills' spoken meanings don't warm: they come up typed, and a key and a tap are needed before anything is said.

### Saved progress and settings

Progress is the one thing the app can't lose; the README's "Saved progress" section and REVIEW.md are the rules. In short: change its shape only with a `SCHEMA` bump, a migration and a fixture, or add an optional field with a default. Settings are part of progress. Quiet mode is two settings, `mic` and `sound`; builds before them kept `quiet` and `headphones`, which are read into the two when they're missing and written beside them on every save (`encode`), so an older build still open in another tab or as an installed app keeps quiet too. A word's listening and recall cards are saved under their own keys (`id:listen`, `id:recall`), which an older build keeps as cards it doesn't know; the copies schema 4 made from a word's one schedule carry `split`, so `mergeInto` lets any real answer for that way win over them. The OpenAI key is kept outside it, on purpose, so it never goes into a backup, and with it the estimate of what OpenAI has cost on this device (`pinoy-prompt:openai-spend`): it belongs to the key and this device, not to learning, so Reset leaves it and a backup restored elsewhere does not carry it.

### Tests and CI as one system

- **One pipeline.** `.github/workflows/ci.yml` tests and builds every pull request and every push to `main`, and publishes to GitHub Pages from `main` only after that has passed, using the build it tested.
- **One runner.** Vitest. Logic tests run in Node; screen tests opt into `happy-dom` with `// @vitest-environment happy-dom` on their first line.
- **Shared test pieces live in `src/test/`.** `screen.ts` has the stand-in `App` (`fakeApp`), `button`, `noMic` and `flush` for screen tests; `fake-speech.ts` stands in for the recogniser and player; `fake-audio.ts` for the shared AudioContext, counting chimes; `fake-storage.ts` for storage; `fixtures/` holds saved progress from every schema. When `App` or `Settings` changes, change `fakeApp` once.
- **Stand-ins go through deps, not module mocks,** where a screen offers them (`SpeakDeps`, `TalkDeps`, `CallDeps`, `Player`). Prefer adding a dep over `vi.mock` of a shared module, which can hide a change in that module from every screen test.
- **Files that can't import each other are checked by a test.** `public/sw.js` can't import from `src/`, so `src/sw.test.ts` checks the cache names and file path it shares with the app. `src/spoken.test.ts` checks every spoken text has its clip, and that Speak passes every card's own clips (and hardly any as a clearly different card), so a change to scoring that would fail the app's own voices fails CI. Add a check like these whenever two systems agree on a name by hand.
- **Screenshots** for UI changes (CLAUDE.md) are taken with `npm run screenshots -- <out-dir> [screen ...]` (`scripts/screenshots.mjs`): Playwright on the dev server, at 360×640, 390×844, an iPhone SE (375×667) and a Pro Max (430×932), the iPhones with their installed safe-area insets, on a seeded learner so before and after match. It always includes Home, and prints Home's scroll height and any screen wider than the phone. It uses Playwright's Chromium (`npx playwright install chromium` once). Add a screen to its list when a change needs one it doesn't reach.

## Findings, October 2026

What a review of the whole app found, most important first, and what has been done.

1. **Two ways out of a drill round.** A drill round showed the page back arrow (to Home) above the session's close button (to the menu): two controls for one job, going to different places. Settings closed with × while Library and Drills used the back arrow. *Fixed: each screen draws its own top, pages with `pageHeader` from `ui.ts`; `src/screens/layout.test.ts` holds them to it.*
2. **Deploy didn't wait for tests.** CI and deploy were separate workflows, so a push to `main` was published even if its tests failed. *Fixed: one pipeline that deploys the build it tested.*
3. **Screen test setup copied eight times.** Each screen test had its own stand-in `App`, and most their own `button` finder, so a change to `App` (as `onBack` was) meant editing every file. *Fixed: `src/test/screen.ts`.*
4. **Service worker names kept in step by hand.** `public/sw.js` repeats two cache names and a source path from `src/`, with a comment pointing at the wrong file. A rename would have broken offline audio or speaking without a failing test. *Fixed: `src/sw.test.ts`.*
5. **Copied UI pieces.** The play / play slowly pair was written out six times across Study and Drills, and the numbered answer choices three times. *Fixed: `audioPair` and `choiceList` in `ui.ts`.*
6. **Study and Drills ask the same questions with separate code.** Read, listen and recall prompts and their feedback are built twice, and the words have drifted: Drills says "Tama!" / "Mali.", Study a rotating "Magaling!" / "Not quite.". *Partly fixed: Study's own extra practice is gone (practice beyond the schedule is Drills', picked by `pickDrillCard`), and guides' gap and build questions are one piece, `screens/guide-question.ts`. Words' prompts and the feedback wording are still built twice; settle them the next time either changes.*
7. **Audio is now one system.** After the clip rewrite, card audio, reference sounds and slices all go through the shared engine, and the built-in voice is only a fallback. The remaining loose end is the visualizer's own context (see Audio).
8. **`screens/session.ts` is large** (about 900 lines: introductions, quizzes, flashcards, guide drills, tile building, speaking, the summary). *Smaller now: speaking left with extra practice, and the gap and build views moved to `guide-question.ts`.*
9. **Screenshots are taken by a new script each time.** Worth a shared `npm run screenshots` (Playwright, Home plus a given screen at 360px and 390px, reporting Home's scroll height and any sideways scroll) the next time a UI change needs them, so REVIEW.md's layout checks are measured the same way every time. *Fixed: `npm run screenshots`, added with the full-height layout.*
